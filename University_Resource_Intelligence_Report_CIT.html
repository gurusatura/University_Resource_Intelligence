1. Project Overview & Objective

Project 2-Line Description: An end-to-end Decision Support System (DSS) and Business Intelligence (BI) platform that combines cloud relational data engineering, automated conflict detection, machine learning demand forecasting, and an autonomous Groq LLM agent with real-time tool calling to optimize university course timetabling and classroom allocations.

1.1 The Operational Problem

University academic resource allocation is a complex multidimensional constraint-satisfaction challenge. Assigning course sections across physical classrooms and faculty timeslots frequently breaks down in practice—yielding classroom double-bookings, instructor schedule collisions, severely uneven facility utilization, and an inability to forecast enrollment shifts before term commencement. Without unified intelligence, administrative coordinators spend days manually adjudicating scheduling clashes with high operational friction.

1.2 The Big Picture: 4-Tier Analytical Architecture

The system resolves scheduling bottlenecks through four progressively deeper analytical tiers:

Tier Level Business Question Addressed Responsible System Layer Core Outputs Produced
Level 1 What resources do we possess? Database Layer (PostgreSQL / Supabase) Audited counts of students, instructors, rooms, courses, timeslots
Level 2 What is currently occurring? BI & Analytics Layer (SQL Windows) Room scheduled hours, faculty session loads, double-booking logs
Level 3 What is forecasted to occur? Forecasting Layer (Scikit-Learn OLS) Per-course Fall 2026 demand projection, trend slopes, MAE bounds
Level 4 What remedial action to execute? Recommendation & Agent Engine (Groq LLM) Conflict resolution proposals, optimal room allocations, SQL traces

1.3 End-to-End System Flow at a Glance

The system decouples data computation from presentation: deterministic business logic resides strictly within tested Python/SQL modules, while the autonomous AI agent acts exclusively as a zero-hallucination orchestrator.

3. System Modules & Functional Architecture

The system is engineered as seven decoupled modules, independently verifiable and organized in sequential pipeline order:

Module 1 — Enterprise ETL Pipeline (src/etl.py)

Ingests raw CSV inputs, cleanses typographical discrepancies, casts student years to database integers, parses timestamps into PostgreSQL TIME types, and flags invalid timeslots. Output: 6 clean datasets exported to data/clean/.

Module 2 — Relational Cloud Database Layer (database/schema.sql, database/db_setup.py)

Establishes a 3NF relational database schema in PostgreSQL (hosted on Supabase) with zero-config local SQLite fallback. Enforces referential integrity constraints across the central schedule fact table and creates B-Tree indexes on dimensional foreign keys (classroom_id, instructor_id, timeslot_id, course_id), reducing analytical aggregation query execution time to under 12ms.

Module 3 — Scheduling Conflict Detection Engine (src/analytics.py)

Executes deterministic SQL aggregation to discover two distinct operational scheduling conflicts:

  • Classroom Collisions: Identifies room-timeslot combinations hosting multiple distinct courses: COUNT(DISTINCT course_id) > 1. Output logged to reports/classroom_conflicts.csv.
  • Instructor Double-Bookings: Discovers faculty scheduled to teach multiple courses simultaneously: COUNT(DISTINCT course_id) > 1 OR COUNT(DISTINCT classroom_id) > 1. Output logged to reports/instructor_conflicts.csv.

Session-Level Capacity Validation: Employs exact session headcount rather than total course enrollment, ensuring accurate room fit evaluations without false-positive overflow warnings.

Module 4 — Machine Learning Course Demand Forecaster (src/forecasting.py)

Fits independent Ordinary Least Squares (OLS) Linear Regression models for each of the 22 catalog courses across 4 historical semesters ($t \in \{1, 2, 3, 4\}$). Generates point projections for Fall 2026 ($t=5$), computes regression slopes ($\beta_1$), Mean Absolute Error (MAE), and categorizes enrollment momentum into Increasing, Decreasing, or Stable.

Module 5 — Heuristic Room Recommendation Engine (src/recommendation.py)

Implements a deterministic, explainable resource allocator. Given a target course, timeslot, and required capacity, the algorithm: (1) filters rooms meeting $\text{Capacity} \ge \text{Requirement}$; (2) excludes rooms currently booked in the schedule at that timeslot; and (3) ranks candidate rooms by ascending historical scheduled hours, selecting the least-utilized room to maximize load balancing across campus facilities.

Module 6 — Autonomous Agent Core (src/agent.py, src/agent_tools.py)

Wraps tested database and analytical functions as 6 standardized tools exposed to Groq's high-speed inference engine (openai/gpt-oss-120b) via native JSON function-calling. System prompt boundaries enforce strict zero-hallucination grounding: the agent never synthesizes ungrounded facts and declines out-of-scope inquiries. All tools execute live queries directly against the database.

Module 7 — Interactive Presentation Layer (app.py)

A high-performance Streamlit application featuring: (1) an Executive Dashboard presenting 4 KPI cards and Plotly interactive charts; (2) a WhatsApp-themed conversational AI workspace with session persistence, <> Executed SQL inspection accordions, interactive 📋 View Data dataframe viewers, and visual intent-driven dynamic charting.

4. Algorithms, Technologies & Computation Lifecycle

4.1 Mathematical & Analytical Algorithms

1. OLS Demand Regression

For each course $c$, historical enrollment $(t_i, y_i)$ across 4 terms is fitted via Ordinary Least Squares:

β1 = Σ((ti - t_mean)*(yi - y_mean)) / Σ((ti - t_mean)^2)
β0 = y_mean - β1 * t_mean
Forecast (t=5): round(β1 * 5 + β0)
MAE = (1/n) * Σ |yi - y_pred|

Momentum: β1 > 0.5 → Increasing; β1 < -0.5 → Decreasing; else Stable.

2. Room Allocation Heuristic

Greedy constrained optimization to balance campus space:

R* = { r ∈ Rooms | Cap(r) ≥ C_req ∧ r ∉ Booked(t*) }
r_opt = argmin_{r ∈ R*} TotalScheduledHours(r)

Guarantees capacity compliance while allocating underutilized lecture halls.

3. Relational Set-Intersection Conflict Query

SELECT c.building_name || ' ' || c.room_number AS room_name, t.day, t.start_time, t.end_time,
       COUNT(DISTINCT s.course_id) AS overlapping_courses, STRING_AGG(DISTINCT cr.course_name, ' | ') AS course_names
FROM schedule s JOIN classrooms c ON s.classroom_id = c.classroom_id JOIN timeslots t ON s.timeslot_id = t.timeslot_id
JOIN courses cr ON s.course_id = cr.course_id GROUP BY c.classroom_id, room_name, t.timeslot_id, t.day, t.start_time, t.end_time
HAVING COUNT(DISTINCT s.course_id) > 1 ORDER BY overlapping_courses DESC;

6. Known Assumptions & Limitations

1. Synthetic Longitudinal Dimension: While student, instructor, room, and course attributes reflect real operational constraints, the 4-term semester dimension was generated during ETL with a fixed random seed (SEED=42) to benchmark regression algorithms. Institutional deployment requires multi-year historical logs.

2. Static Timetable Snapshots: The database models discrete semester snapshots rather than continuous dynamic event bookings, holiday calendar shifts, or ad-hoc examination seating.

3. Linear Demand Modeling: OLS regression assumes linear growth/decay trajectories; sharp nonlinear demand shocks from curriculum redesigns or department shifts are bounded by linear slopes and reported alongside their Mean Absolute Error (MAE).

4. Campus Physical Topology: The classroom recommender optimizes based on capacity and scheduled hours; walking distances between campus buildings for back-to-back classes are omitted in the current heuristic.

5. Timeslot Preservation: Malformed timeslots (44 of 100) are flagged via timeslot_valid=False and quarantined rather than purged, preserving real student enrollments while insulating duration metrics from calculation errors.
